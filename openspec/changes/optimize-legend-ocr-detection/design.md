## Context

**当前状态**：
- 图例 OCR 识别使用固定裁剪底部 30% 的方式
- 裁剪逻辑在前端 `ocr.js` 中通过 Canvas 实现
- 后端 OCR 接口保持不变，接收裁剪后的图片进行识别

**约束条件**：
- 必须保留完整原图保存到图纸库
- 不增加外部依赖（使用小程序原生 Canvas API）
- 图纸格式固定：底部横向图例（色块+色号+数量），上方为方格图案
- 图例高度约占整图 10-20%

**相关文件**：
- `frontend/miniprogram/pages/bead/ocr/ocr.js` - 核心逻辑
- `frontend/miniprogram/pages/bead/ocr/ocr.wxml` - 页面结构
- `frontend/miniprogram/pages/bead/ocr/ocr.wxss` - 样式定义

## Goals / Non-Goals

**Goals**：
- 提供智能检测算法，利用色块间距特征自动识别图例区域
- 提供滑动条微调界面（5%-40%，默认 15%）
- 优化视觉反馈（虚线边界 + 半透明遮罩）
- 实现防抖机制（300ms）和超时处理（500ms）
- OCR 识别失败时提供手动输入入口

**Non-Goals**：
- 不记录裁剪区域设置（每次重新设置）
- 不修改后端 OCR 识别接口
- 不支持复杂图例格式（仅支持底部横向排列的固定格式）
- V1 版本不实现复杂检测算法（如线条检测、AI 辅助），仅实现基于色块间距的简单检测

## Decisions

### 1. 前端实现智能检测算法

**决策**：使用 Canvas API 在前端进行图像分析

**理由**：
- 即时反馈，无需等待后端响应
- 不增加后端复杂度
- 利用小程序原生能力，无外部依赖

**替代方案**：后端使用 sharp/opencv 处理后返回坐标
- 被拒绝的原因：增加网络请求延迟，后端复杂度提高

### 2. 色块间距检测算法（V1 简化版本）

**决策**：从底部向上扫描，分析每行像素的密度变化和间距特征

**算法细节**：
- 将图片按行扫描，计算每行的"内容密度"（非白像素比例）
- 从底部向上查找第一个"密度突变点"（图例区→空白→图案区）
- 如果 500ms 内未找到合适边界，使用默认值 15%
- 后续版本可优化：加入线条检测、颜色模式识别等更复杂算法

**理由**：
- 简单可靠，实现成本低
- 利用图例区域的明显特征（色块有间距 vs 图案色块紧挨）
- 超时机制确保用户体验

**替代方案**：
- A) 检测矩形线条（方格边框）
- B) 基于颜色/纹理模式识别
- 被拒绝的原因（V1）：复杂度高，可靠度不确定，留待后续优化

### 3. 防抖机制

**决策**：拖动滑动条时等待 300ms 后更新裁剪边界显示

**理由**：
- 避免频繁更新导致性能问题
- 300ms 既能减少更新次数，又不会感觉延迟

**替代方案**：
- A) 实时更新（可能卡顿）
- B) 松手后更新（反馈不够即时）
- 被选中的 C 方案平衡了性能和体验

### 4. 视觉反馈样式

**决策**：
- 裁剪边界：虚线显示
- 裁剪区域内：正常显示
- 裁剪区域外（上方图案）：半透明遮罩

**理由**：
- 虚线清晰表示边界
- 裁剪区域正常显示，用户可以确认内容
- 上方区域半透明，突出裁剪区域

### 5. 超时和失败处理

**决策**：
- 智能检测超过 500ms：使用默认值 15%，显示提示"未能自动识别图例区域"
- OCR 识别后无结果：显示空结果页面 + "添加图例"按钮

**理由**：
- 超时机制保证用户不会等待过久
- 默认值 15% 覆盖大部分情况
- 手动输入入口作为兜底方案

## Risks / Trade-offs

### Risk 1: 智能检测准确率不足
**描述**：基于色块间距的简单检测可能无法准确识别所有图纸

**缓解措施**：
- 提供滑动条手动调整，用户总能修正
- 超时后使用默认值 15%，覆盖大部分情况
- V1 作为基础版本，后续可优化算法

### Risk 2: 大图处理性能问题
**描述**：Canvas 处理大图可能导致性能问题

**缓解措施**：
- 设置超时 500ms，避免长时间阻塞
- 防抖机制减少频繁更新
- 后续可考虑图片压缩或降采样处理

### Risk 3: 色块间距检测算法局限性
**描述**：某些图纸可能没有明显的间距特征

**缓解措施**：
- 超时后回退到默认值
- 用户可手动调整
- 收集失败案例，后续优化算法

### Trade-off: 简单算法 vs 高准确率
**描述**：V1 采用简单算法，可能准确率不如复杂算法

**权衡**：
- V1 优先实现基础功能和用户调整能力
- 后续版本可根据反馈优化检测算法
- 用户手动调整是最终的兜底方案

## Migration Plan

**部署步骤**：
1. 修改前端 `ocr.js`，添加智能检测和滑动条逻辑
2. 修改 `ocr.wxml`，添加滑动条组件和裁剪边界显示
3. 修改 `ocr.wxss`，添加裁剪边界和遮罩样式
4. 测试各种图纸场景
5. 发布小程序新版本

**回滚策略**：
- 保留原有固定裁剪 30% 的代码逻辑
- 如果新版本出现问题，可快速回退到旧版本

**兼容性**：
- 向后兼容：新版本不影响已有的图纸数据和 OCR 结果
- 用户无需迁移数据
